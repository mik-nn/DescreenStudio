# Repository Guidelines

## Контекст проекта

**Descreen Studio Pro** — кроссплатформенное приложение для удаления полиграфического растра и муара со сканов печатной продукции. Текущая версия (v3.7) — одностраничное браузерное приложение на классических методах (2D FFT, фильтры Баттерворта, guided denoise). Цель — нейросетевая версия на стеке PyTorch → ONNX → Rust/Tauri + Svelte (см. `ImplementationPlan.md`).

## Project Structure & Module Organization

- `descreening_studio_pro.html` — весь текущий продукт: UI + движок обработки в одном файле. При изменениях логики искать секции по комментариям-маркерам.
- `ImplementationPlan.md` — **источник истины** по архитектуре целевой системы. Все решения сверяются с ним; расхождения фиксируются в `JOURNAL.md`.
- `Программа подавления растра и муара.md` — исходная концепция/спецификация алгоритмов (рус.).
- `Data/` — DESCAN-18K (zip-архивы, **не распаковывать Train.zip без необходимости** — 35 ГБ). Датасет **не используется для обучения** (лицензия CC BY-NC-SA, офисные МФУ-сканы не соответствуют продакшн-входу). Роль — только референс дефектов.
- `TASKS.md` / `JOURNAL.md` / `WORKFLOW.md` — управление работой, обновлять по правилам `WORKFLOW.md`.
- `knowledge/` — база знаний: источники данных, параметры растра, метрики.
- Планируемая структура (создавать по мере этапов): `ml/` (синтез датасета, обучение), `src-tauri/` (Rust), `src/` (Svelte).

## Ключевые инженерные решения (уже приняты)

1. **Данные: только синтетика + собственные сканы.** GT — коммерчески чистые источники (Unsplash Lite, DIV2K, собственный рендер документов). См. `knowledge/data-sources.md`.
2. **Симулятор растра — двухкаскадный:** «виртуальная печать» в эквиваленте 2400–4800 DPI → «виртуальный сканер» (поворот 0.1–2°, даунсэмпл до 300/600 DPI). Муар должен возникать как алиасинг при ресемплинге, а не накладываться постфактум.
3. **Baseline:** качество v3.7 на реальных сканах — планка, которую нейросеть обязана превзойти. Метрика остаточного растра — энергия пиков в 2D FFT (детектор из v3.7).
4. **Метрики плана (PSNR > 34, SSIM > 0.95) — только на синтетике**, где GT пиксельно-точный.

## Coding Style & Naming Conventions

- Язык документации и комментариев к архитектуре — русский; код, идентификаторы, коммиты — английский.
- Python (ML-пайплайн): типизация, dataclass для конфигов, параметры симуляции — только через явные конфиг-объекты, никаких «магических» констант внутри функций.
- Воспроизводимость: везде, где есть случайность, — явный `seed`; сгенерированные датасеты сопровождаются JSON-манифестом с параметрами.

## Commit Guidelines

- Conventional Commits: `feat:`, `fix:`, `docs:`, `data:`, `ml:`, `refactor:`.
- Коммиты не содержат бинарных данных > 5 МБ (датасеты и модели — вне git, через `Data/` и артефакты).

## Правила для агентов

- Перед началом задачи читать `TASKS.md` (текущий статус) и свежие записи `JOURNAL.md`.
- Каждое архитектурное решение, меняющее `ImplementationPlan.md` или параметры данных, фиксировать записью в `JOURNAL.md` (формат в `WORKFLOW.md`).
- Не менять веса метрик и критерии приёмки без обновления `ImplementationPlan.md` и записи в `JOURNAL.md`.
